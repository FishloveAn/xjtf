# Godot 引擎参考 · 钉死版本

> 本文件记录项目钉死的引擎版本与 API 注意点。**升级引擎版本前先全量跑 `项目文档/04-测试/04-测试-冒烟测试清单.md`。**

## 钉死版本

- 引擎：**Godot 4.7.x stable**（目标 4.7.1；4.7.x 最新维护版均可）
- 语言：**GDScript**（禁用 C#，见 tech-plan §1.2 / ADR-001）
- 渲染：Forward+（Windows 桌面端）
- 物理：**Jolt**（4.4 起为 Godot 3D 默认物理引擎）
- 多人：内置 ENetMultiplayerPeer + MultiplayerAPI（Synchronizer / @rpc）

## M0 用到的 API 注意点（2026-08 核对）

| API | 用法 | 备注 |
|---|---|---|
| `multiplayer.multiplayer_peer = peer` | 挂 ENet peer | `multiplayer` 是 SceneMultiplayer，进程级唯一 |
| `ENetMultiplayerPeer.create_server(port, max_clients)` | 建房 | 端口被占用返回错误码，需检查 |
| `ENetMultiplayerPeer.create_client(ip, port)` | 加房 | 只代表发起成功，最终结果看 `connection_failed` |
| `multiplayer.peer_connected / peer_disconnected` | 对端加入/断开 | 在 `SceneMultiplayer` 上，不是 ENet 上 |
| `multiplayer.connected_to_server / connection_failed / server_disconnected` | 客户端侧三信号 | 客户端专用 |
| `@rpc("any_peer", "call_local", "reliable")` | 客户端→服务器请求 | 服务器内必须校验 `is_server()` + `get_remote_sender_id()` |
| `@rpc("authority", "call_local", "reliable")` | 服务器→所有人广播 | 客户端调用会被引擎忽略（安全网） |
| `MultiplayerSynchronizer.replication_interval` | 同步频率（秒） | 0.05 = 20Hz（tech-plan §10 玩家同步指标）；4.7 属性名为 `replication_interval`（`sync_interval` 已移除，勿用） |
| `SceneReplicationConfig` | 勾选要同步的属性 | 支持同步脚本自定义属性（如 `pitch`） |
| `SceneReplicationConfig.add_property()` | 注册同步属性 | 必须先 `add_property()` 注册，再 `property_set_replication_mode()` 设模式；属性路径用 `NodePath(".:属性名")`（`.` 指同步器 root_path 根节点，`:` 分隔属性名；根节点属性不可省略 `.:` 前缀，否则被当作子节点路径解析失败） |
| `set_multiplayer_authority(id)` | 指定节点 authority | 生成网络节点后调用；authority 端本地控制 |
| `CharacterBody3D.get_gravity()` | 取项目重力 | **返回 `Vector3`（重力向量，非标量）**，默认 `(0, -9.8, 0)`；做竖向速度计算必须取 `.y`：`velocity.y = velocity.y - get_gravity().y * delta`（FULLFIX 踩坑，见 M1-FULLFIX 节） |

## M1-S1 用到的 API 注意点（2026-08 核对）

| API | 用法 | 备注 |
|---|---|---|
| `MultiplayerSynchronizer.set_multiplayer_authority(id)` | 指定同步器权威 | **血量（服务器权威）与位置（客户端权威）不可共用同一同步器**：位置用 PlayerSync（authority=玩家 peer），血量用独立 HealthSync（显式 set_multiplayer_authority(1)），否则客户端会把自己本地的血量值反向广播覆盖服务器 |
| 同一子树多个 MultiplayerSynchronizer | 各配各的 SceneReplicationConfig | 支持共存；RPC 复制由就近同步器处理（S1 未在 Health 上开 RPC，S2/S3 注意） |
| `Node.add_to_group("players")` | 运行时入组 | 配合 `get_tree().get_nodes_in_group()` 让 HUD/丧尸找玩家，避免长引用链（tech-plan §8.4） |

## M1-S2 用到的 API 注意点（2026-08 核对）

| API | 用法 | 备注 |
|---|---|---|
| `@rpc("any_peer")` 请求 + `@rpc("authority")` 广播混合在同一状态节点 | 客户端→服务器请求用 any_peer；服务器→所有人广播用 authority | 前提：状态节点 `set_multiplayer_authority(SERVER_ID)`（服务器权威），否则 authority 广播会被当作"非权威调用"被接收端拒绝。**本节点权威 ≠ 所属玩家 peer**，取所属玩家用 `parent.get_multiplayer_authority()` |
| 同一子树两个 MultiplayerSynchronizer 的 RPC 归属 | PlayerSync（root=Player，客户端权威）与 HealthSync（root=Health，服务器权威）并存 | 节点 RPC 由**最近的同步器 root** 归属（Health 属 HealthSync）；因此 Health 上的广播 RPC 走服务器权威通道 |
| `minf(a, b)` | 进度钳制到 1.0 | 纯展示本地动画（revive_progress 不跨端同步，由广播驱动） |

## M1-S3 用到的 API 注意点（2026-08 核对）

| API | 用法 | 备注 |
|---|---|---|
| `PhysicsDirectSpaceState3D.intersect_ray(query)` | 服务器物理空间复判 | 入口 `Node3D.get_world_3d().direct_space_state`；query 用 `PhysicsRayQueryParameters3D.create(from, to, mask, exclude)`；**exclude 射手 `CollisionObject3D.get_rid()`**（相机在胶囊体内，不排除会自伤）；`collide_with_areas=true` 才能命中 Area3D 命中区域；返回 Dictionary（`collider` 键） |
| `JSON.parse_string(str)` | 解析 weapons.json | 返回 Variant，需判 `is Dictionary`；`FileAccess.open(path, READ).get_as_text()` |
| `Basis.looking_at(dir, up)` | 瞄准基准 | 朝上/朝下时换 up 参考轴，否则报错（spread 应用） |
| 武器节点权威 = 服务器 + WeaponSync | 弹药/换弹服务器权威 | 与 PlayerState/HealthSync 同模式；客户端"是否本机武器"用**父节点 Player 的 is_multiplayer_authority()**（武器节点权威已是服务器，不能直接判断） |
| `request_fire(origin, dir, target_id)` | 客户端→服务器开火 | target_id 为客户端命中预览（S3 传 -1），**服务器以自身 intersect_ray 为准**（防"打空气"）；伤害经 damageable.take_damage → HealthSync 隐式广播，不额外 apply_damage RPC（避免重复结算） |

## M1-S5 用到的 API 注意点（2026-08 核对）

| API | 用法 | 备注 |
|---|---|---|
| 碰撞层方案（丧尸） | 丧尸身体 `collision_layer=4`（敌人层，不在武器射线 mask 内）、`collision_mask=5`（世界1+敌人4） | **丧尸身体不能与命中区同层**：武器 mask 1\|3（世界+命中区）不含丧尸身体层（4），射线才稳定命中 Hitbox（层3），避免身体/命中区重合时优先命中身体而无伤害 |
| `Area3D.get_overlapping_bodies()` / `has_overlapping_bodies()` | 近战判定 | S5 AI 实际用**距离判定**（服务器确定性更好）；AttackArea 节点保留供 M2 动画/范围扩展（editor_description 已注明） |
| `Engine.get_physics_frames()` + 静态计数器 | 分帧预算 | 每物理帧放行前 MAX_AI_PER_FRAME 只丧尸更新，其余轮询下帧（tech-plan §5.4）；静态变量跨实例共享 |
| `MultiplayerSpawner` 自动复制 | `Zombies` 容器 + `ZombieSpawner`（spawn_path） | 与玩家 Spawner 同模式：服务器 `add_child` 即自动复制到所有端；丧尸 `set_multiplayer_authority(SERVER_ID)` 先设再入树 |
| `CharacterBody3D.get_gravity()` / `move_and_slide()` / `is_on_floor()` | 丧尸简化移动 | 每 1.5s 重算朝向（`atan2(-dir.x, -dir.z)` 使 -z 朝向目标），中间按缓存方向直线移动 |
| **Vector 字段复合赋值**（`velocity.y -=` / `position.x +=` / `rotation.y -=`） | **GDScript 4 不支持字段复合赋值** | 解析器把 `velocity.y -= x` 当成 `velocity (y -= x)`，LHS 还是 Vector3、RHS 是 float → 报 `Invalid operands "float" and "Vector3"`。**必须显式写** `velocity.y = velocity.y - x`（先取字段、显式计算、再赋值）。全局禁用 `.x/.y/.z += / -= / *= / /=`（DEBUG03 踩坑） |

| API | 用法 | 备注 |
|---|---|---|
| `GPUParticles3D`（one_shot/restart/finished） | 一次性血雾 | `explosiveness=1.0` 一次爆发、`lifetime=0.6s`、`amount=12`（预算内）；`restart()` 重播；`finished` 信号 → `queue_free` 自动清理（防泄漏） |

## M1-FULLFIX 用到的 API 注意点（DEBUG 修复，引擎实证）

| API | 用法 | 备注 |
|---|---|---|
| `CharacterBody3D.get_gravity()` | 竖向速度积分 | **4.x 返回 `Vector3`（重力向量），不是标量**。`velocity.y - get_gravity() * delta` → `float - Vector3` → 解析报 `Invalid operands "float" and "Vector3" for "-" operator`。**必须** `get_gravity().y` 取竖向分量（DEBUG02/DEBUG03 踩坑：player_controller.gd:217 与 zombie_ai_common.gd:99 同型） |
| **Vector 字段复合赋值**（`velocity.y -=` / `position.x +=` / `rotation.y -=`） | **GDScript 4 不支持字段复合赋值** | 解析器把 `velocity.y -= x` 解析为 `velocity (y -= x)` → LHS Vector3、RHS float → `Invalid operands "float" and "Vector3"`。**必须显式** `velocity.y = velocity.y - x`（先取字段、显式计算、再赋值）。全局禁用 `.x/.y/.z += / -= / *= / /=` |
| 修复验证基线 | `--headless --import` 必须 0 ERROR | 仅 `--import` 会漏检未引用脚本；追加 `--script` 全量 load 所有 `.gd` + 实例化所有 `.tscn` 双重实证（FULLFIX 用 check_all_scripts.gd / check_all_scenes.gd） |

## M2-S3 用到的 API 注意点（2026-08-05 核对，对象池/加压实测踩坑）

| API/坑 | 用法 | 备注 |
|---|---|---|
| **off-tree 节点设 `global_position`** | 报 `Condition "!is_inside_tree()" is true. Returning: Transform3D()` | `set_global_position` 需先读全局变换（get_global_transform 要求已入树）。**对象池回池/出池前复位必须用本地 `position`**（复位清零用 `position=Vector3.ZERO`），入树后再设 `global_position`。M1"先入树再设 global_position"的延伸 |
| **加载期循环依赖 → `Parse Error: Busy`** | AI 脚本引用 `ZombiePool` 类 + 池脚本 `const X := preload(zombie_common.tscn)` | 加载链 场景→AI→池→场景 成环 → `Parse Error: Busy [Resource file zombie_common.tscn:38]`。对策：**AI 不引用池类类型**（经 `get_first_node_in_group` 动态 `call("despawn_to_pool", ...)`）；池改用**运行时 `load()`** 装载场景（setup 时）而非 preload |
| **对象池 off-tree 节点泄漏** | `queue_free` 只级联在树内子节点 | 池预实例化节点不进场景树 → 池被 free 时它们**不**随树级联释放 → 退出报 `ObjectDB instances were leaked`（128 只 ≈ 1400 对象）。对策：池 `_exit_tree()` 手动 `queue_free` 池内所有节点 |
| **`--script` 工具脚本编译期引用游戏类** | 工具脚本 `as ZombieHealth` / `ZombieAI.State.IDLE` | 工具脚本编译在 autoload 注册**之前**，引用丧尸类会拉其脚本 → `Identifier not found: NetworkManager` 编译失败。对策：工具脚本一律**动态访问**（`health.get("hp")` / `int(ai.get("state"))`），不写类型注解 |
| died 信号重复连接 | 池化复用同一节点 | 每次出池重复 `connect(died, _on_zombie_died.bind(z))` → 一次死亡触发 N 次计数/回池。对策：**is_connected 判重只连一次**（Callable 按 对象+方法+bound 参数判等，`is_connected` 可识别重新构造的 bind） |

## M2-S4 用到的 API 注意点（2026-08-05 核对，补给点实测踩坑）

| API/坑 | 用法 | 备注 |
|---|---|---|
| **无 RPC 上下文时 `get_remote_sender_id()` 返回 0** | 服务器进程**本地直接调用** `@rpc("any_peer")` 函数体（如单机/主机玩家按 E 直接调 `request_pickup()`） | 函数内 `var sender = multiplayer.get_remote_sender_id()` 得 0，找不到 players 组对应玩家 → 请求被拒（debug_pickup 实测 A/B 拾取不生效）。对策：**`if sender == 0: sender = multiplayer.get_unique_id()`**（无 peer 时 unique_id=1=服务器玩家 authority，兜底本地调用）；RPC 请求路径（客户端 rpc_id 到服务器）仍用 remote_sender_id，安全不降级 |
| 工具脚本 `var x := node.dyn_prop` 类型推断失败 | `--script` 工具脚本读游戏节点动态属性（`state.hp` / `weapon.mag_current`） | 节点是 Node 类型，属性返回值 Variant → `:=` 推断报 `Cannot infer the type`。对策：**显式类型注解** `var hp_before: float = state.hp` |
| 已释放节点再查询 | `await` 后补给点已 queue_free | `node.is_queued_for_deletion()` 对已 free 对象抛 `Cannot call method on a previously freed instance`。对策：用 `is_instance_valid(node)` 判断存在性 |
| `MultiplayerSpawner` spawnable_scenes 为空 | 服务器 add_child 到容器即复制所有端（Pickups + PickupSpawner） | 沿用 M1-S5 丧尸模式：spawn_path 指向容器、不配 spawnable_scenes，服务器 `add_child` 即自动复制；预置场景节点（main.tscn 静态补给点）不走 Spawner，拾取消失走 `pickup_used` authority 广播让所有端本地 queue_free |
| 静态类函数跨脚本调用 | `SupplyPoint.refresh_from_reward(...)`（WaveManager 调用） | supply_point.gd 不引用 wave_manager → 无加载环；工具脚本不能静态调用（编译期引用游戏类失败，M2-S3 铁律），引擎实证经 WaveManager._enter_intermission 触发 |

## M2-S5 用到的 API 注意点（2026-08-05 核对，headless 双实例联机模拟实测踩坑）
> 背景：S5 联机验收用 `godot --headless --path . --script tools/debug_lan_sim.gd -- --server/--client`
> 双进程模拟局域网，期间用探针脚本（场景挂脚本，headless 正常模式）交叉验证，确认以下为 4.7 通用行为。

| API/坑 | 用法 | 备注 |
|---|---|---|
| **`MultiplayerSpawner.add_spawnable_scene(path)` 参数是 String** | 传场景路径 | 4.7 签名 `add_spawnable_scene(path: String)`，传 PackedScene 报 `Invalid argument ... should be "String" but is "Resource"`（探针实测，先查 API） |
| **Spawner 必须配 `spawnable_scenes` 否则复制失败** | Player/Zombie/Pickup 三个 Spawner 均 `add_spawnable_scene`（两端执行） | 实测：spawnable_scenes 为空时服务器 add_child 照常广播，但**客户端**收到 spawn 包后 `instantiate_scene` 用空数组取 p_id=0 → `Index out of bounds (spawnable_scenes.size() = 0)` → 节点不创建，随后同步器刷 `Node not found`。**修复**：main.gd._ready 对三个 Spawner 注册场景（M2-S5 修复 commit）；两端顺序须一致（客户端按 p_id 索引实例化） |
| **同步器 authority 必须在 `_enter_tree` 设置** | 玩家用 `name.to_int()`（节点名=str(peer_id)） | 4.7 报 `MultiplayerSynchronizer ... unable to process the pending spawn since it has no network ID. This might happen when changing the multiplayer authority during the "_ready" callback`。**复制到客户端的本地权威玩家副本**会因此创建失败（玩家 A 能看到但自己的玩家/远端玩家看不到）。修复：main.gd 玩家名改 `str(peer_id)`，player_controller `_enter_tree` 里 `set_multiplayer_authority(name.to_int())`（官方推荐模式） |
| **工具脚本 lambda 修改外层局部变量不可靠** | lambda 回写一律用**成员变量** | 实测：`connected_to_server.connect(func(): got_conn=true)` 信号触发（lambda 执行了）但外层 `got_conn` 仍 false。GDScript 4 lambda 对局部变量的写捕获不可靠，成员变量才生效（debug_lan_sim 全员改成员变量后 PASS） |
| **headless ENet 客户端 peer id 非固定 2** | 动态取 `get_peers()[0]` / `get_unique_id()` | headless 双实例下客户端 peer id 是**大数**（如 1492345957），不是真机的 2。**测试脚本禁止硬编码 peer id 2**，用动态值（游戏代码本身全动态，无影响） |
| **服务器主动断开的时机** | `multiplayer.multiplayer_peer = null` 后保持进程运行 | 客户端 server_disconnected 靠 **ENet 超时**触发（本地无断开帧，等待可达 30s+）；显式 `ENetMultiplayerPeer.close()` 在已从 multiplayer 移除后调用会**卡住主循环**（675 次 No multiplayer peer 刷屏 + await 挂起）。对策：断开后多等（测试脚本 20s）或等对端确认标记；真机正常流程（关窗口进程退出）不受影响 |
| **服务器 spawn 前客户端场景须就绪** | Spawner 复制包**不会补发历史节点** | 服务器 spawn 时客户端若还没进主场景，复制包被丢弃且永不重发（客户端永远缺玩家/丧尸）。真机靠 main.gd `SPAWN_GRACE_SECONDS=0.5`（两端同时切场景）；测试脚本用**客户端就绪标记**（user:// 共享文件）让服务器等客户端场景就绪后再进主场景 |
| **`--script` 工具脚本也受上述 Spawner/Synchronizer 规则约束** | 探针用「场景挂脚本 + headless 正常模式」交叉验证 | 两种方式下复制行为一致（都不自动复制未配 spawnable_scenes 的节点），证明上述规则是 4.7 通用行为，非工具脚本特有限制 |

## M2-S3 性能实测与渲染选型（2026-08-05，headless 引擎实证）
- **实测环境**：Godot 4.7.1 headless（无渲染，FPS = CPU 帧率；场景=主场景波3「潮涌」burst 30 只，独立 MeshInstance3D×30 + ZombieSync + Jolt CharacterBody + 分帧 AI）。
- **实测数据**：30 只同屏采样 5s —— CPU 帧率 avg≈145 / min≈144（CPU 帧时间 ≈6.9ms，远低于 60fps 的 16.7ms 预算）；击杀 30 只 → Zombies 容器子节点回落为 0、池 idle=128/active=0（无泄漏）；二次出池 30/30 复位合格（hp=100/state≠DEAD/collision(4,5)/visible/scale=1），无死尸复活。
- **渲染选型结论**：30 只独立 MeshInstance3D 在 M2 规模下 CPU 帧时间 6.9ms 达标 → **简化方案足够，MultiMesh 延后至 M3（100 只里程碑）**。届时按 art 规格实现 MultiMeshInstance3D + 顶点色动画掩码（R=腿/G=臂/B=头躯干，M1 BoxMesh 无动画可简化为位移摆动）。丧尸部分 draw call 30（=实例数），M2 以"60fps 实测达标"为准，20 draw call 指标随 MultiMesh 在 M3 达成。
- **分帧 AI**：`MAX_AI_PER_FRAME=40 ≥ 30`，30 只场景每帧全额更新（预算机制生效，不触发轮询丢帧）。

## M3-S4 性能基线（2026-08-06，headless 加压实测 30→60→100）

- **实测环境**：Godot 4.7.1 headless（无渲染，CPU 帧率）；主场景波 3 改造为**纯 common burst** 加压波（特感隔离，`tools/debug_pool_perf.gd` 运行时覆写 `wm._waves[2]`）；独立 MeshInstance3D×N + ZombieSync + Jolt CharacterBody（简化胶囊）+ 分帧 AI（`director.json ai_budget=80`）。
- **实测数据**（每档采样 5s）：
  | 同屏数 | fps_avg | fps_min | 平均帧 | 最大单帧 | physics tick/5s |
  |---|---|---|---|---|---|
  | 30（基准，S3 同口径 6.9ms） | 145.0 | 145 | **6.90ms** | 10.0ms | 300/300 |
  | 60（常驻目标） | 144.9 | 144 | **6.90ms** | 10.2ms | 300/300 |
  | 100（峰值上限） | 144.8 | 144 | **6.90ms** | 10.8ms | 300/300 |
  注：6.90ms = headless idle 地板（空载 6.85ms），三档均贴地板 → 实际负载 <6.9ms；physics tick 300/5s 证明 100 只 AI+物理无滞后；最大单帧 ~10ms（burst 收尾瞬时峰值）仍 <16.7ms。
- **判定**：**100 只独立实例 CPU 帧时间 <16.7ms，60fps 达标（裕量 ≥2.4×）→ 简化方案足够，MultiMesh 延后**（M3 任务卡 §2-S4「先测再优化」）；draw call 100 只=100 次（预算内），MultiMesh 的 ≤20 draw call 指标与顶点动画留待 art 低模就位 + 真机渲染剖析（M3-S8）时再评估。丧尸部分渲染侧已补 `visibility_range_end=60m`。
- **对象池**：128 容量**确认够用**（100 峰值 + 特感不池化、独立实例化 → 不扩 192，避免无谓内存/启动成本）；MAX_CONCURRENT=100 不变。
- **无泄漏**：每档击杀后 Zombies 容器回落 0、池 idle=128/active=0；池复用再刷 100 只复位 100/100 合格（hp/state/collision/visible/scale，无死尸复活）。
- **波次配置**（waves.json）：3 波递进 20→45→80（composition/concurrent_cap 同步放大），波 3 = 78 common + charger 1 + spitter 1，同屏峰值 80（60-80 常驻口径）；100 为硬上限由加压测试覆盖（非正式波次）。特感配额保持 ≤2/波（同屏特感 ≤5 director cap）。
- **降级开关**：director.json `degrade.enabled=true, max_concurrent=100` 启用预留（实测 100 只达标未触发；实际由 waves.json concurrent_cap 约束，tech-plan §11 风险 1 缓解就位）。
