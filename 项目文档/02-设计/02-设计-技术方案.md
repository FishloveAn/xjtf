# 技术方案：类求生之路2 合作 PVE FPS（Godot 4）

> 项目代号：L4D-like
> 编写：engineering-lead（程基岩） | 版本：v1.0 | 日期：2026-08-04
> 定位：全项目技术地基。本文档面向"1 人开发 + AI 协作"，所有内容必须**可直接照做**。
> 配套文档：`项目文档/03-开发/03-开发-场景职责总表.md`（场景/脚本/职责总表，随开发更新）

---

## 0. 一句话架构

> **Godot 4.7（稳定版）+ GDScript + 内置多人（ENet + MultiplayerSynchronizer/Spawner/RPC），Windows 桌面端，Listen Server（主机权威），局域网 4-8 人合作 PVE FPS。服务器全权决定：血量/伤害/刷怪/波次/掉落/胜负；玩家位移采用"客户端预测 + 服务器宽松校验"保手感。**

本方案所有决策都以「**1 个人 + AI 能长期维护**」为第一优先级，性能其次，画面最次。

## 1. 技术选型定案

### 1.1 Godot 版本：**4.7.1 stable（或 4.7.x 最新维护版）**

| 项 | 决定 | 理由 |
|---|---|---|
| 引擎 | Godot **4.7.1** stable | 当前（2026-08）最新稳定线；4.6 起官方进入"性能优化"阶段，4.7 含 stencil buffer 等渲染增强；对 3D 大量实例更友好 |
| 语言 | **GDScript**（不用 C#） | 见 1.2 |
| 物理引擎 | **Jolt**（4.4 起为 3D 默认） | 对大量 kinematic 角色体、raycast 明显优于旧 GodotPhysics，适合高密度丧尸 |
| 渲染 | Forward+（桌面端默认） | Windows 独享，无兼容负担；Low Poly 完全够用 |
| 多人底层 | **ENetMultiplayerPeer**（内置） | 为局域网/低延迟设计，内置可靠/不可靠通道；无需自建 UDP 协议 |
| 多人高层 | 内置 MultiplayerAPI：`MultiplayerSynchronizer` + `MultiplayerSpawner` + `@rpc` | 官方组件，AI 训练语料充足，出坑资料多 |
| 网络发现 | 手动输 IP（MVP）→ UDP 广播发现（扩展期） | MVP 别碰发现协议，直接输 192.168.x.x:5555 |

**钉版本纪律**：在 `project.godot` 与 `项目文档/03-开发/03-开发-引擎版本记录.md` 记录钉死版本。AI 生成的代码必须基于该版本 API；升级引擎版本前先全量冒烟测试。

### 1.2 GDScript vs C#：**选 GDScript**（本场景的明确结论）

| 维度 | GDScript | C# |
|---|---|---|
| AI 语料丰富度 | **极高**（官方教程/论坛/示例几乎全是 GDScript） | 少一个数量级，AI 生成正确率明显低 |
| 迭代速度 | 改完即跑，无编译 | 需要 .NET SDK + 编译，AI 报错排查链更长 |
| 环境复杂度 | 单 exe，零额外依赖 | 需装 .NET SDK，版本匹配易翻车 |
| 性能 | 本场景够用（瓶颈在渲染与 AI 预算，见 §5） | 更快但用不上 |
| 引擎功能接入 | 完整、零胶水 | 部分高级功能需 C# 侧适配 |

**结论**：1 人 + AI 开发、局域网 4-8 人、100 丧尸、Low Poly —— 性能不构成瓶颈，GDScript 的迭代与 AI 友好度是决定性优势。**全项目禁止混用 GDScript + C#**（心智负担翻倍）。

### 1.3 多人 API 选型：**内置 MultiplayerAPI，不引第三方**

- 官方高层 API（MultiplayerSynchronizer / MultiplayerSpawner / @rpc）在 Godot 4.4+ 已成熟，配合 ENet 足够覆盖本需求。
- 不需要：WebSocket（面向公网/浏览器）、第三方库（如 Nakama/Steamworks —— 本项目局域网、无账号体系，全部不需要）。
- 自定义需求（丧尸快照、兴趣管理）在优化期用**自定义快照通道**补（见 §4.4、§5.3），不换框架。

### 2.2 命名与目录规范（AI 协作铁律）

1. **文件/节点一律 snake_case**：`zombie_common.gd`、`wave_manager`、`attack_area`。
2. **一个场景 = 一个脚本 = 同名**：`player.tscn` ↔ `scripts/player/player_controller.gd`。场景根节点挂同名脚本，例外情况写入 `项目文档/03-开发/03-开发-场景职责总表.md`。
3. **纯数据放 `data/*.json`**，脚本只做"读取 + 应用"。调数值 = 改 JSON，AI 不用理解代码。
4. **autoload 单例用 PascalCase**（`NetworkManager`），与普通场景脚本区分。
5. **禁止 move/rename 文件**（除非全局搜索引用并同步更新）。`.tscn` 内 `ext_resource` 是绝对路径 `res://...`，一改名就断链，AI 排查成本极高。
6. 脚本单文件 **≤ 300 行**；超了必须拆分（拆到 core/ 纯逻辑或 data/ 数据）。

### 3.0 场景树阅读约定

```
节点名 (节点类型)  — 职责说明
                    └─ 子节点
```

### 3.1 主场景 `scenes/main/main.tscn`

```
Main (Node3D)                        — 游戏入口，装配一切；启动时读取房间配置
├── World (Node3D)                   — 世界根（地图/光照/刷怪容器）
│   ├── Environment (WorldEnvironment)  — 天空/雾/环境光（Low Poly 氛围）
│   ├── Sun (DirectionalLight3D)     — 主方向光 + 阴影
│   ├── Level (Node3D)               — 关卡实例（environment/test_level.tscn）
│   │   ├── Geometry (StaticBody3D)  — 墙壁/地板碰撞（collision_layer=1）
│   │   ├── Visual (MeshInstance3D*) — 关卡网格（可多 Mesh）
│   │   ├── NavRegion (NavigationRegion3D) — 丧尸可行走区域（烘焙导航网格）
│   │   └── SpawnPoints (Node3D)     — 刷怪点集合（子节点 Marker3D，按组"spawn_point"标记）
│   └── Zombies (Node3D)             — 丧尸容器 [Authority=server]
│       └── (动态生成: zombie_common / zombie_special 实例)
├── Gameplay (Node3D)                — 玩法逻辑
│   ├── WaveManager (Node)           — 波次状态机（§7）
│   ├── Director (Node)              — 简化 AI 导演：压力计算/刷怪节奏（§7）
│   └── Pickups (Node3D)             — 掉落物容器（弹药/医疗包）
└── UI (CanvasLayer)                 — 全部 UI（不持有游戏状态，只读展示）
    ├── HUD (Control)                — 血条/弹药/波次提示
    └── Scoreboard (Control)         — 计分板/结算
```

**关键点**：
- `Zombies`、`Pickups` 是**服务器唯一写权限**的动态容器（§4.2）。
- UI 层**只读游戏状态**，通过信号或 `game_state.gd` 拿数据，绝不直接改玩法数据（防"UI 与服务器状态打架"）。

### 3.2 玩家角色 `scenes/player/player.tscn`

```
Player (CharacterBody3D)             — 玩家；本地玩家响应输入，远端玩家只做插值显示
│   [MultiplayerSynchronizer: 同步 position/rotation.y/health/current_weapon]
├── Head (Node3D)                    — 视角根；只旋转 X（俯仰 pitch），clamp ±89°
│   └── Camera3D                     — 第一人称相机（仅本地玩家启用）
├── Body (MeshInstance3D)            — 他人视角可见的模型（第三人称显示用）
├── Collision (CollisionShape3D)     — 胶囊碰撞（collision_layer=2, mask=1）
├── WeaponPivot (Node3D)             — 武器挂点（枪口世界坐标由此计算）
│   └── Weapon (Node3D)              — 当前武器实例（武器基类，§6）
├── Health (Node)                    — 血量逻辑 [Server 权威]
└── Input (Node)                     — 本地输入采集（仅本机玩家活跃）
```

**关键点**：
- 相机**只属于本地玩家**：`Camera3D.current = true` 只在 `is_multiplayer_authority()` 为真时设置。
- 同步的只是**结果状态**（位置/朝向/血量/武器），不是输入。
- 玩家位移由本地控制器执行（客户端预测），服务器定期校验（§4.3）。

## 4. 多人网络架构（关键）

### 4.1 拓扑：Listen Server（主机权威）

```
            ┌──────────────────────────────┐
            │  主机（Host）= 服务器 + 玩家1   │
            │  拥有：所有丧尸 AI、波次、血量、  │
            │  伤害判定、掉落、胜负            │
            └──────────────┬───────────────┘
                           │ 局域网（ENet，端口 5555）
           ┌───────────────┼───────────────┐
           │               │               │
      ┌────┴────┐     ┌────┴────┐     ┌────┴────┐
      │ 玩家2    │     │ 玩家3    │  …  │ 玩家8    │
      │ (客户端) │     │ (客户端) │     │ (客户端) │
      └─────────┘     └─────────┘     └─────────┘
```

- **主机 = 服务器 + 玩家**：同一进程跑全部游戏逻辑 + 自己的一份玩家。
- 客户端**只发输入/请求**，**只接收**服务器广播的状态。
- 无需独立服务器进程（MVP）；优化期提供"无头主机"可选项（§11 风险5）。

### 4.2 同步策略总表（明确：哪些同步、哪些本地、谁算僵尸）

| 数据 | 谁算 | 同步方式 | 频率 | 说明 |
|---|---|---|---|---|
| 本地玩家自身位移 | 客户端 | 客户端预测（本地直接执行） | 即时 | 手感优先；服务器宽松校验（§4.3） |
| 远端玩家位置/朝向 | 服务器 | MultiplayerSynchronizer | 20 Hz | 客户端做插值显示 |
| 玩家血量/状态/武器 | **服务器** | MultiplayerSynchronizer | 事件+定期 | 伤害结算全在服务器 |
| 丧尸位置/朝向/状态 | **服务器** | MVP: Synchronizer / 优化: 自定义快照 | 15-20 Hz | **丧尸 AI 只在服务器跑，客户端纯显示** |
| 丧尸生成/死亡 | **服务器** | Spawner 生成 / 快照移除 | 事件 | 客户端绝不直接生成网络丧尸 |
| 波次状态/倒计时 | **服务器** | RPC 广播 | 事件 | |
| 掉落物/拾取 | **服务器** | Spawner + RPC | 事件 | 拾取请求发服务器校验 |
| 枪口特效/音效 | 客户端 | 本地 | 即时 | 视觉层，不与服务器状态绑定 |
| 命中判定 | 客户端 raycast + **服务器复判** | RPC 请求 | 事件 | 见 §4.3、§6 |

**核心原则：服务器是全游戏唯一"真相源"（source of truth）。客户端的一切修改都是"请求"，由服务器裁决。**

### 4.3 权威划分：为什么玩家位移是"客户端预测 + 服务器校验"而不是纯服务器权威

- **纯服务器权威位移**（客户端只发按键，服务器算移动）：手感会被局域网延迟影响（即使 1-5ms 也有感），且每帧同步输入实现成本高。适合竞技对抗 FPS，不适合本项目。
- **客户端预测 + 服务器宽松校验**（本方案）：玩家本地直接移动，20Hz 上报位置；服务器校验"位移速度是否超上限/是否穿墙"（宽松，防明显作弊/卡 bug），异常则回滚修正。合作 PVE 局域网下这是**标准务实做法**，实现量少一个数量级，AI 好维护。
- **命中判定**：客户端 raycast 决定"我打中了谁/哪里"（保证手感），把 `(目标id, 部位, 伤害)` 发服务器；服务器**复判**（距离、目标存活、弹药余量）后结算。局域网下几乎无感知差异，防"打空气"类作弊。

### 4.4 RPC 使用规范（强制）

| 类别 | 注解 | 调用方式 | 示例 |
|---|---|---|---|
| 请求类（客户端→服务器） | `@rpc("any_peer", "call_local", "reliable")` | 客户端 `rpc_id(1, "request_damage", ...)` | `request_damage(target_id, dmg, hit_pos)`、`request_pickup(item_id)`、`request_fire(origin, dir)` |
| 广播类（服务器→所有人） | `@rpc("authority", "call_local", "reliable")` | 服务器 `rpc("apply_damage", ...)` | `apply_damage(target_id, new_hp, attacker_id)`、`wave_started(n)`、`zombie_died(id)` |
| 状态同步 | MultiplayerSynchronizer 节点（非 RPC） | 编辑器勾选属性 | position/rotation/health/weapon |

**强制规则**：
1. **所有会改变服务器状态的函数必须 `@rpc("any_peer")` 且内部校验来源**——客户端永远无法直接调用服务器私有逻辑。
2. **服务器广播一律 `@rpc("authority")`**，客户端调用会被 Godot 直接忽略（安全网）。
3. 伤害/扣血/扣弹药/刷怪/波次推进/拾取 —— **五类操作只准走服务器**，写成清单贴进 `项目文档/03-开发/03-开发-控制清单.md`。
4. 快照类大流量用**不可靠通道**（`unreliable`），事件类（死亡/波次）用**可靠**。局域网带宽宽裕，但习惯先立好。
5. `rpc_id(1, ...)` 里 `1` = 服务器 peer id（Godot 约定）；禁止写死魔法数，用 `NetworkManager.SERVER_ID = 1` 常量。

### 4.5 断线 / 主机迁移：**MVP 不做主机迁移，做"断线告知 + 可重开"**

- **结论**：4-8 人局域网合作，**不做主机迁移**。理由：迁移 = 全量状态快照 + 新主机重建所有丧尸/波次 + 所有权转移，是多人游戏最高风险模块之一，1 人 + AI 预算下极易翻车，收益（主机退后游戏继续）在熟人局域网场景价值低。
- **MVP 行为**：主机退出 → 所有人收到 `host_left` 提示 → 返回主菜单 → 原主机重开房（进度由主机本机存档 `save/progress.json` 保留：波次号、分数、玩家装备）。其他人可加入新房间。
- **优化期可选**：客户端掉线重连（同一局，断线 30s 内可重连回同一房间）——低优先，不阻塞。

## 5. 高密度丧尸优化方案（50-100 只同屏）

### 5.0 先定目标

- MVP：**30 只**同屏（用简单做法，先验证玩法）。
- 优化期：**100 只**同屏稳定 60 FPS（主机优先）。
- 手段优先级：**减少 CPU（AI/导航）> 减少 GPU 绘制（MultiMesh）> 减少带宽（兴趣管理）**。

### 5.1 渲染路径：**MultiMeshInstance3D（合并绘制）+ 顶点着色器动画**（正式推荐）

| 方案 | 100 只时 | 结论 |
|---|---|---|
| 每只一个 MeshInstance3D + 骨骼动画 | 100 次 draw call + 100 套骨骼 | ✗ 不可行 |
| **MultiMeshInstance3D**（普通丧尸）+ 顶点着色器做简单动画 | **1-2 次 draw call**，逐实例 transform 由 CPU 更新 | ✓ **主方案** |
| GPU 粒子替代丧尸本体 | 只是特效，不能当可被击杀的单位 | ✗ 仅用于血雾等特效 |
| 骨架动画个体 | 每只有独立 Skeleton3D | ✓ 仅用于**特感**（数量 ≤ 5） |

**具体路径（照做）**：
1. 美术出一个低模人形（**500-1200 三角形**，见 §10 规格），顶点骨骼权重尽量少。
2. `MultiMeshInstance3D` 设置 `multimesh.instance_count = 128`（容量留余量），网格用该低模。
3. **动画**：不做骨骼动画，用**顶点着色器**做"行走摆动 + 手臂下垂晃动"：每个实例通过 `set_instance_custom_data()` 写入 `(相位, 移动速度, 变体种子)`，shader 里 `sin(phase + t*speed)` 驱动少量顶点位移。Low Poly 风格下观感完全够。
4. **每帧**：服务器更新每个丧尸 transform → 主机把活跃实例的 transform 批量写入 `multimesh.set_instance_transform(i, xform)`；**不可见实例设 transform 为远离视野的位置**（避免剔除负担）。
5. 死亡表现：非特感丧尸"倒地淡出"（shader alpha 淡出或直接消失 + 血雾粒子），不做布娃娃（100 个布娃娃是灾难）。

### 5.2 剔除与裁剪

- Godot 4 自动做视锥剔除；**开 OccluderInstance3D**（关卡内墙/转角）做遮挡剔除。
- 每实例用 `visibility_range_begin/end`：远处丧尸淡出（性能 + 观感双重收益）。
- 阴影：MultiMesh 阴影一次 draw call 代价低，但只给**近玩家 25m 内**实例开 `cast_shadow`，远处关（shader/自定义数据控制）。

### 5.3 带宽：**自定义快照 + 兴趣管理**（优化期）

MVP 用官方 Spawner/Synchronizer（简单、能跑）。到 100 只时：
- 服务器每 15-20Hz 广播一帧"丧尸快照"：`zombie_id, x, y, z, rot_y, state, hp_ratio`（约 15-20 字节/只），用 `PackedByteArray` 打包 + 不可靠通道。
- **兴趣管理**：对每个客户端只发**该客户端 40m 半径内**的丧尸（100 只里通常只有 30-50 只在视野内）→ 每客户端带宽 ≈ 30-50 只 × 20B × 20Hz ≈ **12-20 KB/s**，局域网毫无压力。
- 客户端维护**对象池**（§5.5），按快照更新位置，做**插值**（保留上帧+本帧，`lerp` 平滑）。

### 5.4 AI/导航：**分级 AI + 简化导航**

| 丧尸类型 | 导航方式 | 单只成本 |
|---|---|---|
| 普通丧尸（90%） | **不跑 NavigationAgent3D**；直线/朝向目标移动 + CharacterBody 撞墙物理；每 **1.5s** 才重新算一次朝向；无避障（互相推挤，正是丧尸海观感） | 极低 |
| 特感（≤5 只） | 完整 `NavigationAgent3D` + 避障，路径每 0.5-1s 重算 | 中 |

- **每帧 AI 预算上限**：每帧最多更新 N 只丧尸的 AI（如 40 只），其余轮询（分帧）。防止一帧卡死。
- NavigationServer3D 本身多线程；**导航网格（NavMesh）在关卡编辑期烘焙**，运行时只查路径不重烘焙。
- 丧尸"看见"玩家：用**距离 + 简单 LOS（raycast）**，不做视觉锥/听觉复杂系统（导演系统决定谁醒，见 §7）。

### 5.5 对象池（必做）

- `zombie_pool.gd`：预实例化 128 只丧尸节点（隐藏），`spawn_from_pool(point, type)` / `despawn_to_pool(z)`。**避免运行时反复 instantiate/free**（这是 100 只丧尸卡顿的头号元凶）。
- 死亡特效（血雾 GPUParticles3D）同样用粒子池。

### 5.6 物理

- 丧尸用 `CharacterBody3D`（kinematic 式），**禁用 RigidBody3D**。
- 碰撞形状一律**简化胶囊**（不做脚/躯干细分碰撞）。
- Jolt 物理引擎（4.7 默认）对大量 kinematic 体 + raycast 性能好；命中检测在**服务器物理空间**做 `PhysicsDirectSpaceState3D.intersect_ray`（§6）。

## 6. 第一人称控制与武器系统

### 6.1 第一人称：CharacterBody3D + Head + Camera3D（官方标准姿势）

```
Player (CharacterBody3D)
├── Head (Node3D)          ← 只绕 X 轴转（俯仰 pitch），clamp ±89°
│   └── Camera3D           ← current = true 仅限本地玩家
└── (Body 只做他人视角显示)
```

- 鼠标移动：`InputEventMouseMotion` → `yaw`（绕 Y，作用于 CharacterBody）+ `pitch`（绕 X，作用于 Head）。
- 移动：`_physics_process` 里读 `Input.get_vector()` → `velocity` → `move_and_slide()`。
- 跳跃/下蹲按需；**重力走 CharacterBody 默认模板**。
- 关键：**Head 与 Body 分离**是 FPS 第一原则（俯仰不能转身体），这个结构 AI 生成时极易搞错，写进控制清单。

### 6.2 武器系统：**hitscan（射线判定）+ 数据驱动**

- 命中检测用 **hitscan 逻辑**（`intersect_ray`），**不用投射物**（子弹飞行的物理子弹在本游戏没必要）。RayCast3D 节点也可，但服务器复判需要服务器物理空间，统一用代码 raycast 更干净。
- **武器 = 数据**（`data/weapons.json`）+ 行为脚本（`weapon_base.gd`）：

```json
{
  "id": "pistol",
  "damage": 25, "fire_rate": 5.0, "mag_size": 12, "reload_time": 1.2,
  "spread_deg": 1.5, "range_m": 60.0, "auto": false,
  "sound": "sfx/pistol.ogg", "muzzle_offset": [0.0, -0.02, -0.4]
}
```

- **射击流程（标准 hitscan）**：
  1. 客户端：本地播枪声/枪口火花/后座动画（纯视觉，立即响应）。
  2. 客户端：从 `Camera3D` 世界原点 + 朝向（加 spread 扰动）做一次 raycast 找"命中预览"（只用于准星反馈）。
  3. 客户端：`rpc_id(1, "request_fire", origin, dir, target_id)` 发服务器。
  4. 服务器：校验弹药/射速冷却 → 在**服务器物理空间** `intersect_ray` 复判 → 命中则结算伤害 → `rpc("apply_damage", ...)` 广播。
  5. 客户端收到广播后播放命中特效（血雾/命中点）。

- **换弹/切枪**：同样走服务器（`request_reload` → 服务器计时 → 广播弹匣状态）。客户端只做本地动画。

## 7. 波次 / 导演系统架构（类 L4D"AI 导演"简化版）

### 7.1 职责划分

| 系统 | 职责 | 反职责（不做） |
|---|---|---|
| **WaveManager** | 波次状态机、波次定义装载、波次开始/结束/奖励 | 不做具体刷怪节奏 |
| **Director** | 持续计算"压力值"，决定刷怪节奏/特感时机 | 不做波次结构 |
| **Spawner（WaveManager 内）** | 按 Director 指令从对象池刷怪/回收 | 不决定"刷多少" |

### 7.2 WaveManager 状态机

```
Setup ──(倒计时结束/玩家就绪)──▶ WaveActive ──(本波目标达成)──▶ WaveCleared
  ▲                                                              │
  └────────────── Intermission（休整：补血/弹药/购买）◀────────────┘
        (倒计时后自动进入下一波 Setup/或玩家提前触发)
```

- 波次定义在 `data/waves.json`（AI 可改）：

```json
{
  "id": "wave_03",
  "name": "潮涌",
  "composition": { "common": 60, "runner": 3, "tank": 1 },
  "concurrent_cap": 60,
  "spawn_style": "trickle",
  "spawn_interval": 1.2,
  "cleared_when": { "type": "all_spawned_killed" },
  "reward": { "health_packs": 2, "ammo": 1 }
}
```

### 7.3 Director（简化 AI 导演）：数据结构 = 压力值

- **压力值** `pressure ∈ [0,1]`，每 0.5s 更新一次：

```
pressure = clamp(
  0.4 * (1 - 存活玩家占比)      # 人越少越紧张
+ 0.3 * (1 - 场上丧尸/上限)     # 丧尸越少越要补
+ 0.3 * (本波已过时间/期望时长)  # 拖太久自动加压
, 0, 1)
```

- 用法：`spawn_interval = base_interval * (1.6 - pressure)`；`pressure > 0.7` 时允许刷特感（数量 ≤ 配置上限）。
- **特感时机**：用"事件触发器"（kill_ratio / 玩家位置转移 / 固定计时），不做 L4D 级复杂行为树。
- **数据全部在 `data/director.json`**，改手感不改代码。

### 7.4 推荐数据结构（脚本内）

```
WaveManager:
  current_wave: WaveConfig(Dictionary)   # 来自 waves.json
  state: enum { SETUP, ACTIVE, CLEARED, INTERMISSION }
  spawn_queue: Array[dict]               # 待刷丧尸（类型+时间戳），Director 填
  spawned_count / killed_count: int

Director:
  pressure: float                        # 每 0.5s 重算
  special_cooldown: float                # 特感冷却
  params: Dictionary                     # 来自 director.json

ZombiePool:
  pool: Array[Zombie]                    # 空闲池
  active: Dictionary[int, Zombie]        # id → 活跃丧尸
  spawn_from_pool(type, pos) / despawn(z)
```

## 8. AI 协作工作流（重点）

### 8.1 黄金闭环（每任务必走）

```
① 写任务卡（一句话目标 + 验收标准）
        ↓
② 让 AI 生成/修改代码
        ↓
③ 运行验证（F5 或调试场景）
        ↓
④ 有错？→ 复制报错原文 + 文件路径 + 行号 → 回传 AI → 回②
        ↓
⑤ 无错？→ 对照验收标准逐条确认 → Git commit（一个小目标一个 commit）
```

- **每个循环只做一件小事**（如"让丧尸能被手枪打死"），循环时长目标 ≤ 半天。禁止让 AI 一次生成整个系统。
- **报错回传模板**（粘给 AI）：

```
文件：res://scripts/weapons/weapon_base.gd:42
报错：<Godot 输出面板原文，整段复制>
期望：开火后弹匣-1，且播放 pistol 音效
已尝试：把 animation.play 移到 _physics_process 无效
```

### 8.2 文件粒度与命名（见 §2.2，此处补充"为什么"）

- **一个文件 ≤ 300 行**：AI 上下文窗口有限，小文件 = AI 一次能读完整个文件再改，出错率骤降。
- **一个场景一个职责**：调试时只开该场景，报错定位快。
- **纯数据 JSON**：数值平衡 AI 改 JSON 不碰代码，不会改坏逻辑。

### 8.3 注释规范（AI 可读优先）

```gdscript
## zombie_ai_common.gd — 普通丧尸状态机（只在服务器运行）
## 职责：Idle→Chase→Attack→Dead；不负责导航寻路（用简化朝向）
## 输入：@export chase_range / attack_range；由 WaveManager 经 spawn 激活
## 输出：修改自身 velocity；死亡时发 zombie_died 信号
## 谁调用：仅服务器（客户端该脚本不激活）

func _physics_process(delta: float) -> void:
    # 分帧预算：每帧只更新部分丧尸，防止一帧卡死（§5.4）
    ...
```

- **头部块注释**固定格式：职责 / 输入 / 输出 / 谁调用（AI 3 秒看懂一个文件）。
- **@export 变量**必须写注释说明含义 + 单位：`@export var chase_range: float = 15.0  # 米，超过此距离丧尸不追击`。
- 关键决策行写"为什么"（如 `# 用不可靠通道：位置丢失比延迟更可接受`）。

### 8.4 让 AI 高效理解场景树

- **维护 `项目文档/03-开发/03-开发-场景职责总表.md` 总表**，一页写完：场景路径 → 脚本路径 → 职责 → 依赖。每次新增场景同步更新。
- 给 AI 喂上下文时**贴 .tscn 片段 + 对应 .gd**，并说明层级意图；不要只给一句"改一下丧尸"。
- 用节点的 **`editor_description`**（.tscn 里是 `editor_description` 字段）给关键节点写中文注释，AI 读 .tscn 直接看到。
- **用组（groups）代替到处查节点**：丧尸组 `"zombies"`、刷怪点组 `"spawn_point"`、玩家组 `"players"`。AI 用 `get_tree().get_nodes_in_group("zombies")` 即可，不写长引用链。
- 一条铁律：**场景文件 .tscn 尽量用编辑器改**（AI 手改 .tscn 极容易把节点 id/资源路径改坏）；AI 改代码，人/编辑器改场景。

### 8.5 测试与验证策略

- MVP 不做自动化单元测试（1 人团队负担过重），做**冒烟清单**：`项目文档/04-测试/04-测试-冒烟测试清单.md` 列出每阶段 10-20 条"能跑什么、验证什么"（§9 落地）。
- 建 **Debug 控制台**（autoload/debug_console.gd，仅开发构建编译）：`spawn 50`、`kill_all`、`god`、`wave next`、`teleport`。AI 调试效率提升 10 倍。
- 每个子系统配**独立调试场景**（`tests/scenes/test_zombie_ai.tscn` 等），不依赖主流程就能验证。

### 8.6 版本与协作纪律

- 全程 Git；**每个完成的小目标一个 commit**，消息写"做了什么 + 验证了什么"。
- **场景文件冲突规则**：.tscn 是文本但 diff 难读 → **同一时间只有一个人（或 AI）改一个 .tscn**；AI 改代码、人改场景，天然错开。
- move/rename 前必须全局搜 `res://旧路径` 引用（§2.2 规则 5）。

## 10. 性能预算（硬指标，写进控制清单）

| 指标 | 目标值 | 备注 |
|---|---|---|
| 帧率 | **主机 60 FPS（第一优先）**；客户端 60 目标 / 30 底线 | 主机兼任服务器，主机卡 = 全员卡 |
| 同屏丧尸 | MVP 30 → 优化期 **100**（常驻 60-80 + 特感 ≤ 5） | 见 §5 |
| 玩家同步 | 20 Hz | MultiplayerSynchronizer |
| 丧尸同步 | 15-20 Hz（快照） | 客户端插值 |
| 带宽 | 每客户端 **< 100 KB/s**（优化后实际 15-25 KB/s） | 局域网 100Mbps 起步，余量极大 |
| 包体 | 打包 exe **< 600 MB**（目标 400 MB） | Low Poly + 压缩纹理 |
| 运行时内存 | **< 2 GB** | 低模资产 + 对象池 |
| 三角面预算 | 普通丧尸 **500-1200 tris**；特感 2000-4000；玩家 ≤ 3000；环境单体 ≤ 5000 | 详见 §10.1 美术规格 |
| draw call | 全场景 **< 500**（丧尸部分用 MultiMesh 后 ≤ 20） | Forward+ |

### 10.1 给 art-director 的资产技术规格（摘要，详见 §10 表格 + 交付消息）

- 普通丧尸：**500-1200 三角形**（瘦型 600-1,000 / 壮型 800-1,200），单张 512² 图集贴图（或共享 1024² 大图集），**无骨骼**（顶点着色器动画，§5.1）。**顶点色通道 = 动画掩码：R=腿 / G=臂 / B=头躯干（已与 art-director 对齐，2026-08-04）**，顶点色禁止他用。行走摆动用 MultiMesh `custom_data` 相位偏移防整群同步；不做几何 LOD，靠 `visibility_range`(60m) + Distance Fog 淡出。
- 特感：2000-4000 三角形，**标准骨骼**（AnimationPlayer），动画数 ≤ 6（idle/walk/attack/hurt/death/spawn）。
- 玩家：≤ 3000 三角形，第一人称只需看到手臂+武器（第三人称模型可简单）。
- 材质：**StandardMaterial3D（或 ORM）单张纹理，禁 PBR 多层贴图**（Low Poly + 性能双赢）；半透明/发光材质数量 ≤ 5 个。
- 贴图：一律 2 的幂（256/512/1024），`import` 时开压缩（VRAM Compressed）。
- 环境：单体 ≤ 5000 三角；关卡尽量**合并静态网格**（少 draw call）；提供 Occluder 用的粗盒/粗面。
- 所有模型**导出 .glb**（Godot 原生导入，AI/版本控制友好），禁止 .fbx 直挂。

### 10.2 给 design-strategist 的性能约束（摘要）

- **同屏丧尸数上限：100（常驻 60-80）**，波次 composition 总和不要设计超过它；特感同屏 ≤ 5。
- 丧尸速度/体型受 AI 简化限制：普通丧尸**不做复杂寻路**（直线推进 + 撞墙），设计上避免"需要丧尸绕复杂迷宫"的地形。
- 玩家数硬上限 8。
- 波次时长/数量设计要匹配导演压力模型（§7.3），避免"长时间 100 只全在场"的极端配置。

## 11. 技术风险与缓解（Top 5）

### 风险 1：100 只丧尸把 CPU/GPU 打爆（最可能翻车）
- 症状：主机帧率掉到 20 FPS，全员跟随卡顿。
- 缓解：§5 全套（MultiMesh 合并绘制、顶点动画、简化导航、分帧 AI 预算、对象池）；**先做 M0 性能冒烟**（30 只 → 50 → 100 逐步加压，记录帧率曲线）；预留"丧尸降级"开关（同屏超阈值自动削减刷怪，`director.json` 可配）。

### 风险 2：多人同步抖动/穿墙/伤害不一致
- 症状：玩家瞬移、丧尸滑步、打了不掉血。
- 缓解：局域网低延迟下先做**最小同步原型**（M0 就是为此）；插值（远端玩家/丧尸一律插值显示）；服务器权威结算伤害（§4.4）；每局开启 `debug` 同步日志（记录每帧收发字节/丢包）。

### 风险 3：Godot 多人 API 的坑（Spawner/Synchronizer/RPC 权限）
- 症状：客户端"看不到"丧尸、RPC 没触发、`MultiplayerSpawner` 生成节点错乱。
- 缓解：**网络节点一律由服务器生成**（客户端只接收）；Spawner 的 `spawn_path` 指向服务器拥有的容器（§3.1 `Zombies`）；RPC 权限表（§4.4）贴进控制清单；遇到坑先查官方文档/社区（AI 语料充足），并把坑写进 `项目文档/03-开发/03-开发-架构决策记录.md`。

### 风险 4：1 人 + AI 开发量失控、代码腐烂
- 症状：AI 生成的 1000 行大文件没人敢动；改一个数值动十处。
- 缓解：§8 全套（小文件、数据驱动、模板复制已测脚本、注释纪律、每任务一 commit）；**每阶段结束做一次代码评审**（让 AI 以"新程序员"视角重读项目，输出重构建议）。

### 风险 5：主机兼任玩家 = 性能与公平双输
- 症状：主机玩家体验差（自己机器跑全部 AI），或主机隐作弊（知道丧尸位置）。
- 缓解：性能预算把主机帧率当第一优先（§10）；提供"**无头主机模式**"（单独一台机器 `--headless` 只开服不渲染，玩家用别的机器玩）作为 LAN 聚会可选；隐作弊在合作 PVE 中可接受，不投入反作弊。
